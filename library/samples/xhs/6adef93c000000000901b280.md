## 1. 核心观点（一句话）

作者把 AI 编程受挫归因于准备和工作流程，借个人翻车叙事引出先调研、定要求、拆任务、检查和沉淀模板的做法。

## 2. 目标读者与使用场景

已用 AI 编程工具、能生成演示但难以持续修改交付的人，以及不知道开发流程的新手；适用场景是开始一个小项目和处理后续迭代，而非选模型榜单。

## 3. 内容展开路径

1. 第 1 页用时长和经验身份作承诺，第 2 页先给工具相同但用法不同的判断，转入作者自述的项目经历。
2. 第 3 页叙述从能运行到修改崩坏的落差，再给出需求文档这个转折。第 4–5 页解释为何去 GitHub 看他人工作方式与更新记录。
3. 第 5–9 页把流程拆成任务说明、计划、可检查的交付标准、小步工作、检查项、存档、重开对话、自查和固定模板，用生活化工作比喻组织技术步骤。
4. 第 9–10 页补充日常习惯，第 10–11 页降低开始门槛，收束到跑通一个小任务并保存可复用过程。

## 4. 注意力钩子

- 类型：身份共鸣与经历承诺。
- 原句：标题「每天vibe coding六七小时的心得总结」。
- 机制：用持续投入暗示经验浓度，再用失败经历建立同处境感；实际投入时长与效果未验证，不能直接照搬数字。

## 5. 情绪曲线

- 开头：用长时间使用者的身份引出经验期待。
- 中段：先展示作者自述的修改失败和返工，再用具体动作提供可控制感。
- 结尾：从长清单缩回一个小项目，降低行动门槛；部分效率保证与“无需学完”表述仍需读者自行验证边界。

## 6. 论证方式

个人经历、前后反差、工作类比和流程清单。作者以 GitHub 更新、星数及“官方文档”增加可信感，但没有在本轮提供可独立复核的实验或效率对照。高星不等于适合当前任务，模型自查不等于独立测试，重新对话也不保证解决问题。
