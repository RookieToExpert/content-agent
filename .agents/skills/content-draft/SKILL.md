# content-draft：用自己的真实素材 + 验证过的结构写稿

核心原则：**结构可以学，故事可以编，技术必须真。**每篇都要落回赛道「普通人也能给自己造工具」。

## 开始前必读

1. `AGENTS.md`、`rules/redlines.md`、`rules/ai-tells-zh.md`
2. `positioning.md`（受众、支柱、语气）
3. `library/patterns.md`：优先用「自测有效」>「样本支持」>「假设」；避开「自测无效」
4. `library/demand.md`：选题优先回应出现次数多、还没有去向的需求
5. 写产品稿时必读 `products.md`，只能用里面写明的功能和截图

## 流程

### 1. 选题（用户没指定题目时）

给 3～5 个选题，每个一行：读者 / **普通人为什么会停下来**（热点/反差/有趣经历/能直接拿走） / 我的真实素材 / 对应需求 D-xxx 或热点 / 角色（引流/信任/转化） / 打算用的规律 P-xxx。

选题配比参考 `positioning.md` 的支柱比例；「为什么会停下来」说不出来的题直接淘汰，哪怕它很专业。
**由用户挑**，不要自己定了直接写。

### 2. 澄清（写之前必须回答清楚，缺哪项问用户，一次问完）

1. 读者是谁？
2. 读者此刻的痛点或欲望？
3. 核心结论（一句话）？
4. 技术部分是什么、做没做过？没做过就先真做一遍（或请用户做）再写——**技术演示不能编**
5. 语气：理性分析 / 讲故事 / 情绪共鸣？
6. 有没有产品露出？露出哪个功能？

### 3. 搭结构再写正文

1. 建目录 `posts/<YYYY-MM-DD-slug>/`，复制 `templates/post.md` 为 `post.md`
2. 先写选题卡 + 结构大纲（每段写目的，标注哪段必须用户补真实细节），给用户看一眼再展开
3. 标题至少 3 个候选，分别用不同规律，标出推荐的那个和理由；最终标题写进 frontmatter `title`
4. 正文要求：
   - 先结论，后过程；有具体数字、具体现象、具体判断
   - 段落按人说话的停顿分，不要每句一行
   - 故事角色和情节可以虚构；技术步骤、截图、结果必须来自真实操作，缺的用 `【待补：xxx】` 标出来
   - 涉及自己产品的功能和数据只用 `products.md`
5. 配图计划：每张图一句话说明内容。知识卡片类图片可以生成；**产品图只用真实截图**；终端/页面截图注明哪些地方要打码
6. frontmatter 填 `patterns`、`inspired_by`、`pillar`、`product`、`cta_code`

### 4. 产品宣传稿的写法

- 结构：一个真实场景里的具体问题 → 试过哪些办法不行 → 怎么做出/用上这个工具 → 现在的效果（真实数据或截图）→ 软性提示（主页/私信口令）
- 产品占篇幅不超过一半；删掉产品部分，剩下的内容仍应对读者有用
- 不写价格、不放链接、不用绝对化用语；分配一个新口令记到 `products.md` 的口令表

### 5. 热点稿的写法（时效优先）

- 目标是热点出现后 24～48 小时内发出；可以跳过「先给大纲」这一步，直接出完整稿，但仍要过 check_draft 和用户审核
- 必须有**自己上手的东西**：截图、对比、实测数字、翻车点。只复述新闻的不写
- 开头一句话交代「发生了什么 + 我的结论」，正文给证据，结尾说对普通人意味着什么
- 不确定的信息（传闻、未发布的参数）明确标「据说/未证实」

### 6. 工作见闻和干货的写法

- 工作见闻要找**普通人会觉得意外的点**（钱、规模、反差、人的故事），技术细节只留理解所需的最少部分
- 讲**通用现象 + 判断方法 + 排查顺序**，不讲具体环境
- 去掉/模糊化：公司、集群、节点、IP、域名、内部组件名、精确规模、精确时间
- 组件只写开源名（Kubernetes、Volcano、NCCL…）
- 写完自问：同事看到能不能认出是哪次事故？能认出就继续改

### 7. 自检与交审

1. `python3 scripts/check_draft.py posts/<slug>/post.md`，ERROR 必须清零；WARN 逐条处理或在审核记录里写明为什么保留
2. 自查一遍 `rules/redlines.md` 里脚本查不了的项（截图打码、可定位性、真实性）
3. `status` 改为 `review`，在「审核记录」写下 check_draft 结果
4. 给用户：最终标题、封面文案、正文、配图计划、话题，以及**需要用户补的【待补】清单和需要打码的位置**
5. 用户确认后改 `approved`；用户发布后填 `url`、`published_at`，改 `published`

## 改稿

- 用户改过的稿子，对比 agent 原稿和用户终稿，把用户反复删改的东西（某类词、某种结构）提炼出来，告诉用户并建议加进 `rules/ai-tells-zh.md` 或 `positioning.md` 的语气部分，用户同意后再改

## 不做

- 不编技术步骤、产品功能、产品数据
- 不替用户发布、不替用户回复评论
- 不抄样本原文；`inspired_by` 只是记录结构来源
